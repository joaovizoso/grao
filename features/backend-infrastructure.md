## Summary

Three separate product asks all reduce to "grao needs a place in the cloud to put files, and a way to hand out narrow, temporary access to specific files":

1. **Delivery backend** — booth captures (video/photo/boomerang) upload from the kiosk to a per-event cloud folder during/after the event, so the couple's "private digital gallery" (already sold on both plans) can eventually be a link the founder sends, instead of the operator manually copying files off the iPad and hand-delivering a drive/transfer after the wedding.
2. **Instant guest share** — right after a photo strip or boomerang capture, show the guest a QR code linking to a small per-capture share page (view/save the image, or share-sheet into Instagram/WhatsApp) so they get their own copy on their phone before walking away from the booth, instead of only the kiosk having a local copy.
3. **QR remote recording** (already scoped in its own file) — a guest records on their own phone instead of queuing at the booth; the clip needs to land in the same per-event storage.

All three need: a bucket, per-event folders, and a serverless function that mints short-lived presigned URLs (upload for #1/#3, read/share for #2). One backend, three consumers.

## Field evidence & revised verdict (2026-10-23)

### New evidence (founder-reported)

1. **The local-download save path does not work at an event.** On iPad Safari, every capture's `<a download>` (three call sites: `saveAndFinishVideo`, the photo-strip save, the boomerang save in `index.html`) triggers Safari's download prompt; the guest or operator must tap through a save/open dialog after every single capture. Not operable at a real wedding.
2. **Local storage fills with every capture**, with no lifecycle.
3. Kiosk device confirmed: **iPad Air M3 13"**, landscape, Safari, intended to run as a home-screen web app under Guided Access (hardware plan Option 1). The Pi5/local-hardware-bridge path is further away than before.
4. Context (not yet elsewhere in the repo): the **Canon Selphy CP1500 supports AirPrint**, so on-site printing from the iPad does not need the CUPS/local-backend bridge CLAUDE.md's Hardware Roadmap assumes. Recorded here as context only; the hardware roadmap itself is not rewritten by this entry.

This invalidates the 2026-07-31 premise ("the manual process works, it's just annoying"). The booth's *save path* is broken in the field for every mode on both plans. That is a defect of the same class as Known Issues #1/#2 — arguably worse, since it touches every capture — not a nice-to-have.

### The trap, and the design that avoids it

"Drop the download, upload straight to the cloud" makes the cloud the only copy: a failed PUT on venue WiFi loses a guest's only take. Rejected. The proposed **local outbox** is the right shape: capture → durable write to browser-internal storage → background drain to R2 → delete locally only after the server has verified the bytes.

### Verdict: approve the outbox, with these amendments

**1. Use IndexedDB (Blob values) as the store, not OPFS.** OPFS write support in Safari (`createWritable`) is recent and version-dependent; IndexedDB Blob storage is the long-supported path in WebKit and needs no worker. One store, one code path. Developer must still prove Blob-in-IDB survives an app kill + iPad reboot (test T3) — WebKit has had historical bugs with IDB-stored Blobs becoming unreadable; if T3 fails, fall back to storing `ArrayBuffer`.

**2. Storage eviction / persistence.**
- The 7-day ITP script-writable-storage cap applies to Safari *tabs*; home-screen web apps are exempt and have their own storage container. **Running as a home-screen app is therefore a requirement of this design, not a nicety.**
- Corollary trap: **the home-screen app and a Safari tab on the same URL have separate storage.** A queue built in one is invisible in the other. Operator rule: the booth is only ever opened from the home-screen icon.
- Call `navigator.storage.persist()` on launch and show the result of `navigator.storage.persisted()` in the operator panel. Do not assume it is granted; it's a pre-event checklist item.
- **Deleting the home-screen icon, "Clear History and Website Data", or an iPad reset/restore destroys the un-drained queue.** Operator rule: never do any of these with pending > 0.

**3. Quota at GB scale.** Per-origin quota on a 128GB+ iPad is far above a 2GB worst case; the real risk is the device's own free space. Check `navigator.storage.estimate()` on launch and before each capture; below a threshold (default: 2GB free in quota) show an operator warning; below a hard floor (default: 500MB) show an operator alert. Never refuse a guest silently.

**4. The iPad as single point of failure until upload — acceptable, because it's strictly better than today.** Today the iPad is the SPOF for *every* capture for the whole event (and beyond, until manual hand-off). With the outbox and a live connection, exposure shrinks to minutes per capture. The mitigation is therefore **connectivity, not more code**: the 4G hotspot is no longer optional kit for upload-enabled events, and the operator panel shows **oldest pending age** (target: under 10 minutes when online). If that number grows, the operator knows the safety net isn't working while there's still time to act.

**5. What "confirmed" means before local deletion.** Not "fetch resolved", not "HTTP 200 alone". Confirmed = the server response states the object exists at the expected key **with byte size equal to the local Blob's size and a SHA-256 checksum that R2 validated on write**. The client computes SHA-256 (`crypto.subtle.digest`) before upload and sends it; the Worker passes it to `R2Bucket.put(key, body, { sha256 })`, which makes R2 reject a corrupted body. Only on a confirmed response does the client delete the IDB record.

**6. Amendment to the 2026-07-31 architecture: stream the PUT through the Worker using an R2 binding, instead of presigned S3 URLs, for this consumer.** Rationale: (a) confirmation and checksum validation happen in one round-trip; (b) idempotency is enforced server-side; (c) no long-lived S3 access key needs to live in the Worker as a secret (the R2 binding replaces it) — less credential surface; (d) Worker request bodies up to 100MB are well above a 60s clip (~15–40MB, unverified). The Worker streams, never buffers. If a capture ever exceeds the body limit, presigned URLs remain the documented fallback. Read-scoped presigned URLs for #2 (instant share) are unaffected by this amendment.

**7. Duplicate/idempotent uploads.** `captureId = crypto.randomUUID()` is generated at capture time and stored with the record. Object key is deterministic: `{eventCode}/{YYYYMMDD-HHMMSS}-{mode}-{captureId}.{ext}`. On a retry, the Worker `head()`s the key first; if it exists with the same size and checksum it returns `exists` (treated as confirmed) without rewriting. A re-PUT of identical bytes is harmless anyway. No server-side database needed.

**8. A capture completing mid-flow.** The guest-facing "saved" moment (Thank you screen) is shown **only after the IndexedDB transaction's `oncomplete`** — never before. If the IDB write fails (quota, error), the guest is not told it saved: show a visible alert and fall back to the existing `<a download>` path for that capture (prompt and all) so the take is not lost. Keep that code as the fallback, don't delete it. Upload draining is network I/O and must never gate the screen flow; to protect recording, the drain does not *start* a new upload while on Countdown/Recording/Review screens (an in-flight one may finish).

**9. Safari has no Background Sync API.** "Background worker" here means a drain loop on the open, foreground page. iPad must be in Guided Access, auto-lock Never, on a charger. The drain also runs on app launch, so a queue left un-drained resumes the next time the app opens.

**10. Stuck queue at end of night — operator procedure.** (a) Panel shows pending count, total MB, oldest age, last error. (b) If pending > 0 and the venue network is the problem: **don't clear anything; take the iPad home, open the home-screen app on home WiFi, let it drain to 0.** This is the primary recovery, and it works because the queue persists. (c) Escape hatch if the cloud itself is unavailable: "Export pending" via `navigator.share({ files })` to Files/AirDrop in small batches. Export does **not** delete; deletion still only happens on confirmed upload. There is deliberately no "delete unuploaded" button.

### Pressure-testing the no-cloud alternative

Same outbox, upload disabled, operator bulk-exports at the end. It has no bill, no credentials, no new GDPR surface for the cloud provider. But: (a) it does not fix storage growth, it relocates it; (b) the export can't be confirmed (a share-sheet promise resolving ≠ files verified on a Mac), so there's no safe point to delete; (c) bulk-exporting GBs out of a Safari web app is the least-tested, most likely failure point. **Recommendation stands: cloud.** But the export path gets built anyway as the escape hatch, so the no-cloud mode costs nothing extra: `EVENT.uploadEnabled = false` is the supported fallback if the GDPR prerequisites aren't ready in time for an event.

### GDPR minimum viable answer

**Engineering defaults (reasonable to build now):**
- **Who consents:** each guest, for their own capture. The couple consents contractually as the client but cannot consent on behalf of guests. The couple's contract adds a clause: grao records guest messages at the booth, stores them in an EU-region cloud bucket only to deliver them to the couple, deletes them after N days; the couple receives the content and is responsible for its own copy from then on.
- **Where:** on the Instructions screen (shown before every capture in every mode). One plain-language PT line above the start button, e.g. *"Ao gravar, a tua mensagem fica guardada e é entregue ao João e à Constança. Mais informação no cartão ao lado."* Tapping start is the affirmative act. Plus a printed privacy card at the booth with grao's contact details, purpose, retention, the sub-processor (Cloudflare, EU jurisdiction) and how to request deletion (QR to a short privacy-notice page). The operator is present to answer questions. Video guests can already discard via Retry; photo/boomerang guests can ask the operator. Phase 1 adds an operator-panel "delete last capture" for pending items.
- **Retention:** local copy deleted on confirmed upload. Cloud: an R2 lifecycle rule on the bucket deleting objects **90 days after upload**. The couple is told to download within 60 days. grao keeps no further archive. The lifecycle rule must exist **before the first upload-enabled event**.
- **Region:** create the bucket with R2's **EU jurisdiction** at creation time (it can't be changed afterwards). Accept Cloudflare's DPA.
- **Deletion requests:** manual. Founder finds the object by event + timestamp (keys are time-prefixed) and deletes it in the dashboard. Fine at this volume.

**Needs a real legal check (Portuguese/CNPD-aware lawyer, before the first upload-enabled event):** whether grao is controller or processor relative to the couple (the couple's own use is likely household-exempt, which makes the processor framing awkward); whether the tap-to-record notice is valid consent or whether legitimate interest is the better basis; **minors** (children are routinely at weddings: parental consent, operator guidance); the 90-day retention figure; the contract clause and privacy-notice wording; whether a DPIA is needed (probably not at this scale, but confirm).

## Phased build spec for developer (2026-10-23)

Conventions apply: single HTML file, no npm deps, Safari/iPad first, never fail silently. The Worker is a separate, small, dependency-free JS file (e.g. `worker/upload.js`), deployable by pasting into the Cloudflare dashboard, with no wrangler/npm requirement.

### Phase 1 — Local outbox + verified upload + operator panel (ships as one unit)

Phase 1 must include upload. An outbox without upload turns the per-capture prompt into a bulk-export problem and does not fix storage growth. The internal build order allows testing on the device before the cloud exists: 1a, then 1b.

**1a. Outbox (no network)**
- One `saveCapture(blob, mode, ext)` funnel replacing the three `<a download>` call sites. It writes `{captureId, eventCode, mode, ext, mime, size, createdAt, attempts, lastError}` + Blob to IndexedDB, and resolves only on transaction `oncomplete`. Thank you is shown only after it resolves. On failure: visible alert, then the legacy download fallback.
- `navigator.storage.persist()` on launch. `estimate()` checks with warning/alert thresholds.
- Operator panel behind a deliberate hidden gesture (e.g. 3s long-press on the monogram): pending count, MB, oldest age, `persisted()` state, free quota, last error; buttons for Retry now, Export pending (`navigator.share({files})`, batches of ≤5), and Delete last pending capture (with confirm). No "delete all".
- Discreet Welcome-screen-only indicator: nothing when 0 pending; a small count when pending; an alert tone (not colour alone) when oldest pending is older than 10 min or the last attempt errored. Never shown on capture screens.

**1b. Upload**
- Worker: `PUT /u/{eventCode}/{key}` with an `X-Upload-Token` header. It validates the event code against an allowlist with an active date window (event day ±2), the token, a content-type allowlist (`video/mp4`, `video/webm`, `image/jpeg`), size ≤ 100MB and the key regex. It `head()`s first (idempotency), then `put(key, request.body, { sha256, httpMetadata })`, and returns `{status, key, size}`. CORS is limited to the booth origin. No list/read endpoints.
- Note: the token sits in a static HTML file (public if hosted on public GitHub Pages). That's acceptable *only* because the endpoint is upload-only, time-windowed and capped. The worst case is junk uploads, not data exposure. Rotate the token per event.
- Client drain: one upload in flight. Don't start a new upload during Countdown/Recording/Review. Use an AbortController timeout scaled to size, exponential backoff (5s → 5min cap), and the `online` event plus launch as triggers. Delete locally only on a confirmed response (key + size + R2-validated sha256).
- Bucket: EU jurisdiction, 90-day lifecycle rule, created before the first upload.

**Acceptance criteria:** zero download prompts in all three modes; Thank you is never shown before a durable local write; no local deletion without server-verified size + checksum; the queue survives reload, force-quit and reboot; every failure is visible to the operator within one drain cycle; nothing about upload is guest-facing; works with `uploadEnabled=false`.

**On-device tests (iPad Air M3, home-screen app, Guided Access) — all must pass before a real event:**
- T1: 10 captures per mode, no prompt.
- T2: record the `persist()`/`persisted()` result.
- T3: airplane mode, 30 mixed captures (incl. 60s videos), force-quit, reboot, reopen → all 30 present; network on → drains to 0; R2 count/sizes match; files play on a Mac. **This is the critical test.**
- T4: kill WiFi mid-upload → completes on retry, no duplicate objects, no premature deletion.
- T5: record a 60s video while a large upload is in flight → no recording/UI degradation.
- T6: forced IDB failure (dev flag) → visible alert + fallback download.
- T7: export ≥20 pending (≥500MB) via share sheet to Files/AirDrop; record which batch size works.
- T8: leave 10 pending, close, reopen next day on other WiFi → drains.
- T9: confirm the Safari tab and home-screen app have separate storage; add it to the operator checklist.
- T10: camera/mic permission behaviour across home-screen relaunches.
- T11: 3-hour soak, 100 captures over the 4G hotspot; record real file sizes (replacing the 15–25MB estimate) and the max oldest-pending age.
- Run the Known Issue #2 boomerang playback test in the same session.

**Operator checklist (new):** pre-event: launch from the home-screen icon, persisted = yes, free quota > 10GB, hotspot up, one test capture reaches 0 pending, Guided Access on, auto-lock Never, charger. End of night: pending = 0 before packing; if not, never clear data or delete the app; drain at home.

### Phase 2 — Delivery and hardening (only after Phase 1 runs at a real event)
Couple-facing delivery (a read-only per-event listing or zipped download), a pre-event "storage self-test" screen, and per-event token rotation tooling. Driven by what Phase 1 actually broke, not built ahead.

### Phase 3 — Other consumers (gates unchanged)
Instant guest share (#2): needs Voast/marketer evidence + read-scoped short-TTL URLs + security review. QR remote recording (#3): needs a confirmed Premium client need. Both reuse this bucket and Worker.

## Devil's-advocate take

> **Superseded in part (2026-10-23):** the "nothing has failed yet" premise below is no longer true for the delivery/save path. See "Field evidence & revised verdict" above. Kept as history; the analysis of #2 and #3 still stands.

**Is this justified by evidence yet? Mostly no, with one exception.**

- The delivery backend (#1) is solving a real, already-sold promise ("private digital gallery," both plans) with a manual process that has worked exactly once, at the one wedding that's happened. Nothing has failed yet. The manual-transfer model is annoying for the founder but has not caused a client complaint, a lost file, or a delay anyone has reported. This is "make an existing working process nicer," not "fix something broken" — worth remembering when it competes for time against CLAUDE.md priorities #1–4, none of which are done.
- Instant guest share (#2) is the one with the weakest evidence base of the three: no guest at the one real event asked for this, no marketer research has come back yet on whether it moves bookings, and it's the most feature-shaped ("wouldn't it be cool if...") of the asks. It also measurably increases scope of the backend: #1 only ever needs *upload* presigned URLs (kiosk → cloud, one direction, operator-supervised); #2 needs *read/share* presigned URLs handed to an unsupervised guest's personal phone, plus a share-page UI, plus decisions about how long that link stays valid and who else could access it if guessed/leaked (see Risks).
- QR remote recording (#3) still has the best-documented evidence for existing at all (it's already sold to Premium clients as a line item), but as of last review nobody had confirmed an actual Premium client asked for/needs it in practice — that gate from the original file still stands and isn't resolved by this document.

**Net take: building the full shared backend now, motivated by stacking three speculative-to-semi-speculative asks together, is scope inflation dressed as efficiency.** "We need a backend for X, Y, and Z, so let's build the whole thing" is exactly the pattern where three individually-marginal features add up to justify infrastructure none of them individually justified. The right test isn't "does the unified design make sense" (it does — see Feasibility) — it's "has any single one of these three actually cleared its own bar for building yet." Right now: #1 is closest (real sold promise, real manual pain point that will compound as booking volume grows), #2 is weakest (no demand signal, adds new risk surface for the least-validated payoff), #3 is unchanged/still gated from before.

**What's the smallest version that teaches something before over-building?** Don't build all three consumers. Build the shared primitive (bucket + one presigned-URL function) sized for #1 only — kiosk-side auto-upload of already-captured files into per-event folders, replacing manual USB hand-off, with the *existing* local download also still happening (operator keeps a local copy as the safety net; CLAUDE.md's "no silent fallback that hides failure" principle applies here too — if the upload fails, the local file the guest already has must remain the source of truth, not silently rely on cloud). This alone:
- Validates the serverless-function + bucket architecture end-to-end at a real, low-stakes event.
- Directly reduces the founder's actual recurring manual-transfer workload — a real, unglamorous ops cost, unlike #2 which is speculative guest delight.
- Produces evidence (does upload actually work reliably on venue WiFi/hotspot? what does it cost per event in R2/S3 bills? does anything fail silently?) needed before adding #2 or #3 on top.

> **2026-10-23 note:** "the existing local download also still happening" is no longer viable — the download *is* the broken part. The local outbox (IndexedDB) replaces it as the local safety copy with the same principle: local stays the source of truth until the server verifies the upload.

Only after that's running at a real event should #2 (instant share) or #3 (QR remote) get built on top of the same bucket/function — and #2 specifically should wait for the marketer's Voast research, since "does a comparable competitor's instant-share feature actually drive bookings/reviews" is directly on-point evidence that doesn't exist yet internally.

**Sequencing against CLAUDE.md priorities: this should NOT jump the queue.** CLAUDE.md's Development Priorities are explicit and ordered, and none of the four Known Issues are fully closed (issue #2, boomerang/Safari export, is only "mitigated, not confirmed" per STATUS.md; issue #3, video duration, is only partially addressed; issue #4, the admin/config layer, is still fully open). Recommend treating backend infra as **priority 4.5**: start only after the admin/config layer (priority #4) exists, for a concrete technical reason, not just queue discipline — the config object (`{ plan, features, questions, videoDurationSec }`) is exactly where a per-event bucket path / upload-enabled flag belongs. Building upload logic before the config layer means hardcoding event identifiers into the capture code now and re-plumbing them through the config object later, the same "build it twice" pattern already flagged and avoided for multilingual UI.

## Feasibility / architecture

### Shared primitive (one backend, sized for all three consumers, built incrementally)

- **Storage:** one cloud bucket (Cloudflare R2 recommended over AWS S3 — no egress fees, which matters once guests are pulling photos to their phones under consumer-share traffic patterns rather than a couple pulling a gallery once). Folder structure `bucket/{eventCode}/{captureId}.{ext}`, mirroring the existing per-client single-HTML-file pattern (one event = one folder, same mental model as one event = one HTML file today).
- **Compute:** one serverless function (Cloudflare Worker). Its *only* jobs: (a) verify the caller presents a valid event code / capture-session token, (b) mint a short-lived presigned URL — upload-scoped for kiosk/remote-capture writes, read-scoped for guest share-page reads — and (c) never touch file bytes itself (bytes flow browser↔bucket directly, same as already correctly scoped in qr-remote-recording.md). This keeps the "backend" genuinely thin — no database, no auth system, no server to patch/monitor 24/7. It's a config-lookup-and-token-mint function, not an application server.
  - *2026-10-23 amendment:* for the kiosk upload consumer (#1), the Worker streams the PUT body into R2 via a binding (point 6 of the revised verdict) instead of minting presigned upload URLs. This gives verified confirmation, server-side idempotency and no stored S3 key. It is still no database, no accounts and no buffering. Presigned URLs stay the pattern for read/share (#2) and the fallback for oversized uploads.
- **What has to change in the client-heavy architecture, and what doesn't:**
  - **Stays the same:** capture logic (`getUserMedia`, `MediaRecorder`, canvas compositing for the photo strip and boomerang), the single-HTML-file-per-event pattern, no framework/build step, local download as the guest/operator's copy of record. CLAUDE.md's "no backend" framing becomes "no *application* backend" — there is still no database, no user accounts, no server-rendered pages, no long-running process to operate. *(2026-10-23: the "copy of record" is now the IndexedDB outbox, not a download.)*
  - **Has to change:** the HTML file needs a small amount of new code to (1) read an event code from config, (2) after a successful local capture, `fetch()` a presigned upload URL from the Worker and `PUT` the blob to the bucket (fire-and-forget relative to the guest's flow — the guest already has their local copy; upload happening in the background must never block or gate the existing screen flow, per "a crash mid-recording is a real loss" in CLAUDE.md), and (3) for instant share specifically, request a read-scoped presigned URL and render it into a QR code on the Thank You screen (a client-side QR generator, e.g. a small dependency-free canvas-based QR encoder, is a reasonable, contained exception to "no dependencies" — flag to developer as a decision point, not an assumption).
  - **This does not need "something more"** than client-heavy + thin serverless layer for the sizes involved here (one venue, one event, tens to low hundreds of captures). It would need something more (real backend with a database, auth, job queue) only if grao grows into: multiple simultaneous events needing a shared admin view, server-side processing (e.g. auto-compiling the "edited compilation" Premium feature), or account-based client login to the gallery instead of a link. None of that is in scope here — explicitly flag it as a non-goal for this phase so developer doesn't over-build the Worker into a mini-API.

### Consumer-specific notes

- **#1 Delivery backend:** upload-only presigned URLs, background upload after existing local save, per-event folder. Gallery delivery to the couple is *still* out of scope as an in-app feature per CLAUDE.md's business context ("assume delivery happens out-of-band... until told otherwise") — this just gets the files into the cloud folder; sending the couple a link is still a manual founder action for now (e.g. share the R2 folder or a simple listing page) unless/until that's separately scoped. *(2026-10-23: see Phase 1 spec — outbox + Worker-streamed verified upload.)*
- **#2 Instant guest share:** read-scoped presigned URLs with a **short TTL** (hours, not indefinite) and a page that offers save/share-sheet, not a permanent public gallery page per capture — see Risks below on why indefinite/public URLs are the actual danger here, not the QR code mechanism itself.
- **#3 QR remote recording:** unchanged from its own file; now explicitly consumes the same bucket/function rather than a separate one.

### New risks this introduces (beyond "is it worth building")

- **GDPR/consent, Portugal/EU:** guest video/photo is personal data (arguably special-category-adjacent if it captures likeness at a wedding with identifiable third parties, though not sensitive-category under GDPR strictly). Today, "capture → local file → operator hands off after event" never sends anyone's face/voice off-device. The moment capture uploads to a third-party cloud bucket, grao becomes a data controller/processor making an active choice about where EU citizens' personal data is stored and for how long, and needs: a lawful basis (almost certainly consent, since this is optional guest participation — but consent needs to be actually gathered, not just implied by walking up to a booth), a retention/deletion policy (a bucket with no lifecycle rule effectively becomes indefinite third-party storage of wedding guests' faces — that needs an explicit TTL/deletion job, not an assumption), and a sub-processor disclosure if using a US-headquartered cloud provider (R2/Cloudflare has EU region options — use one, don't default to global). None of this exists today because there's nothing to disclose today (client-side-only, hands-off-locally). This is a materially new compliance surface, not a paperwork footnote, and should be resolved before any guest content leaves the kiosk device, not after a soft launch. *(2026-10-23: concrete minimum answer in "GDPR minimum viable answer" above.)*
- **Instant-share-specific risk:** a read-scoped presigned URL behind a QR code is, practically, "anyone who scans this QR code or has this link can view/download this guest's photo." If the URL is long-lived or the share page is crawlable/guessable, that's an accidental public gallery of wedding guests' photos with no consent flow for the *viewer* side even if the *capturer* consented. Mitigate with short TTLs and non-enumerable capture IDs (already implied by presigned-URL design), but this needs the security review flagged in qr-remote-recording.md before shipping, not just a technical mitigation on paper.
- **Reliability/silent-failure risk (a CLAUDE.md first-class concern):** background upload over venue WiFi/hotspot can fail or stall without the guest or operator noticing, since by design it must not block the existing flow. This needs a visible-but-unobtrusive operator-facing indicator (not guest-facing — don't make guests worry about upload status on their one take) so the operator can tell "local copy: fine, cloud copy: didn't make it, do the USB handoff as backup for this file" — otherwise this quietly reintroduces exactly the failure mode CLAUDE.md's guardrails exist to prevent, just moved from capture-time to upload-time.
- **Cost/ops risk:** bucket storage and a Worker are cheap at one-event scale, but this is the first grao component with an ongoing cloud bill and an account to secure (API tokens, bucket access keys) — a new secrets-management responsibility that doesn't exist in a static-HTML-file world. Small but real, and someone (founder or developer) now owns rotating/protecting those credentials.
- **Storage-container risk (added 2026-10-23):** the outbox lives inside the home-screen web app's storage. Deleting the icon, clearing website data or resetting the iPad destroys un-uploaded captures, and a Safari tab on the same URL sees a different, empty queue. This is mitigated by operator procedure and the oldest-pending-age indicator, not by code.
- **Public upload token (added 2026-10-23):** the per-event token is readable in the HTML. Bounded by upload-only, date-windowed, size/type-capped Worker validation and per-event rotation.
