# Backend Infrastructure (File Hosting + Instant Guest Share)

**Status:** discussing
**Plan tier:** Cross-cutting infrastructure. Delivery/gallery is sold on both plans (Basic + Premium); instant guest-share and QR remote recording are effectively Premium-tier capabilities riding on the same backend.
**Proposed:** 2026-07-31 (architect-strategy, founder-requested — supersedes/merges with [qr-remote-recording.md](qr-remote-recording.md))

## Relationship to qr-remote-recording.md — read this first

This is **not** a second backend. `qr-remote-recording.md` already correctly identified that grao's first backend need is "presigned upload URL via serverless function into an R2/S3-style bucket," sized it, and flagged it needs a security review before building. Everything in this document — file hosting for delivery, and instant guest-facing share — uses that *same* primitive: a bucket with per-event folders, a serverless function that mints short-lived presigned URLs (upload and, now, also download/share), and no long-running server.

**Conclusion: these are one backend, not two.** Treat `qr-remote-recording.md` as one *consumer* of this shared infrastructure (remote capture → upload), alongside two more consumers this document adds (kiosk capture → upload for delivery; kiosk capture → instant share link for the guest). Do not let developer build a second bucket/function pair later for QR remote recording after this one already exists — that would be exactly the "second, incompatible backend" this task warned against.

Action taken: `qr-remote-recording.md` is being updated to cross-reference this file as the architecture source of truth for the backend primitive itself, while keeping its own scope narrowed to what's specific to remote capture (the trimmed capture page, event-code-to-session mapping). This file becomes the place where the shared backend shape, security model, and sequencing decision live.

## Summary

Three separate product asks all reduce to "grao needs a place in the cloud to put files, and a way to hand out narrow, temporary access to specific files":

1. **Delivery backend** — booth captures (video/photo/boomerang) upload from the kiosk to a per-event cloud folder during/after the event, so the couple's "private digital gallery" (already sold on both plans) can eventually be a link the founder sends, instead of the operator manually copying files off the iPad and hand-delivering a drive/transfer after the wedding.
2. **Instant guest share** — right after a photo strip or boomerang capture, show the guest a QR code linking to a small per-capture share page (view/save the image, or share-sheet into Instagram/WhatsApp) so they get their own copy on their phone before walking away from the booth, instead of only the kiosk having a local copy.
3. **QR remote recording** (already scoped in its own file) — a guest records on their own phone instead of queuing at the booth; the clip needs to land in the same per-event storage.

All three need: a bucket, per-event folders, and a serverless function that mints short-lived presigned URLs (upload for #1/#3, read/share for #2). One backend, three consumers.

## Devil's-advocate take

**Is this justified by evidence yet? Mostly no, with one exception.**

- The delivery backend (#1) is solving a real, already-sold promise ("private digital gallery," both plans) with a manual process that has worked exactly once, at the one wedding that's happened. Nothing has failed yet. The manual-transfer model is annoying for the founder but has not caused a client complaint, a lost file, or a delay anyone has reported. This is "make an existing working process nicer," not "fix something broken" — worth remembering when it competes for time against CLAUDE.md priorities #1–4, none of which are done.
- Instant guest share (#2) is the one with the weakest evidence base of the three: no guest at the one real event asked for this, no marketer research has come back yet on whether it moves bookings, and it's the most feature-shaped ("wouldn't it be cool if...") of the asks. It also measurably increases scope of the backend: #1 only ever needs *upload* presigned URLs (kiosk → cloud, one direction, operator-supervised); #2 needs *read/share* presigned URLs handed to an unsupervised guest's personal phone, plus a share-page UI, plus decisions about how long that link stays valid and who else could access it if guessed/leaked (see Risks).
- QR remote recording (#3) still has the best-documented evidence for existing at all (it's already sold to Premium clients as a line item), but as of last review nobody had confirmed an actual Premium client asked for/needs it in practice — that gate from the original file still stands and isn't resolved by this document.

**Net take: building the full shared backend now, motivated by stacking three speculative-to-semi-speculative asks together, is scope inflation dressed as efficiency.** "We need a backend for X, Y, and Z, so let's build the whole thing" is exactly the pattern where three individually-marginal features add up to justify infrastructure none of them individually justified. The right test isn't "does the unified design make sense" (it does — see Feasibility) — it's "has any single one of these three actually cleared its own bar for building yet." Right now: #1 is closest (real sold promise, real manual pain point that will compound as booking volume grows), #2 is weakest (no demand signal, adds new risk surface for the least-validated payoff), #3 is unchanged/still gated from before.

**What's the smallest version that teaches something before over-building?** Don't build all three consumers. Build the shared primitive (bucket + one presigned-URL function) sized for #1 only — kiosk-side auto-upload of already-captured files into per-event folders, replacing manual USB hand-off, with the *existing* local download also still happening (operator keeps a local copy as the safety net; CLAUDE.md's "no silent fallback that hides failure" principle applies here too — if the upload fails, the local file the guest already has must remain the source of truth, not silently rely on cloud). This alone:
- Validates the serverless-function + bucket architecture end-to-end at a real, low-stakes event.
- Directly reduces the founder's actual recurring manual-transfer workload — a real, unglamorous ops cost, unlike #2 which is speculative guest delight.
- Produces evidence (does upload actually work reliably on venue WiFi/hotspot? what does it cost per event in R2/S3 bills? does anything fail silently?) needed before adding #2 or #3 on top.

Only after that's running at a real event should #2 (instant share) or #3 (QR remote) get built on top of the same bucket/function — and #2 specifically should wait for the marketer's Voast research, since "does a comparable competitor's instant-share feature actually drive bookings/reviews" is directly on-point evidence that doesn't exist yet internally.

**Sequencing against CLAUDE.md priorities: this should NOT jump the queue.** CLAUDE.md's Development Priorities are explicit and ordered, and none of the four Known Issues are fully closed (issue #2, boomerang/Safari export, is only "mitigated, not confirmed" per STATUS.md; issue #3, video duration, is only partially addressed; issue #4, the admin/config layer, is still fully open). Backend work is priority-5-adjacent territory (it's explicitly bucketed with "hardware integration — later-stage, only once the browser-side app is stable" in spirit, even though CLAUDE.md's literal priority #5 is hardware, not cloud storage). Recommend treating backend infra as **priority 4.5**: start only after the admin/config layer (priority #4) exists, for a concrete technical reason, not just queue discipline — the config object (`{ plan, features, questions, videoDurationSec }`) is exactly where a per-event bucket path / upload-enabled flag belongs. Building upload logic before the config layer means hardcoding event identifiers into the capture code now and re-plumbing them through the config object later, the same "build it twice" pattern already flagged and avoided for multilingual UI.

**Exception worth flagging to the founder explicitly:** if a second real booking is confirmed before the admin/config layer is finished, and the founder wants delivery-by-link ready for that client, that's a legitimate reason to reorder — but that's the founder's call to make with real booking dates in hand, not something to default into because the backend design is now written down and available.

## Feasibility / architecture

### Shared primitive (one backend, sized for all three consumers, built incrementally)

- **Storage:** one cloud bucket (Cloudflare R2 recommended over AWS S3 — no egress fees, which matters once guests are pulling photos to their phones under consumer-share traffic patterns rather than a couple pulling a gallery once). Folder structure `bucket/{eventCode}/{captureId}.{ext}`, mirroring the existing per-client single-HTML-file pattern (one event = one folder, same mental model as one event = one HTML file today).
- **Compute:** one serverless function (Cloudflare Worker). Its *only* jobs: (a) verify the caller presents a valid event code / capture-session token, (b) mint a short-lived presigned URL — upload-scoped for kiosk/remote-capture writes, read-scoped for guest share-page reads — and (c) never touch file bytes itself (bytes flow browser↔bucket directly, same as already correctly scoped in qr-remote-recording.md). This keeps the "backend" genuinely thin — no database, no auth system, no server to patch/monitor 24/7. It's a config-lookup-and-token-mint function, not an application server.
- **What has to change in the client-heavy architecture, and what doesn't:**
  - **Stays the same:** capture logic (`getUserMedia`, `MediaRecorder`, canvas compositing for the photo strip and boomerang), the single-HTML-file-per-event pattern, no framework/build step, local download as the guest/operator's copy of record. CLAUDE.md's "no backend" framing becomes "no *application* backend" — there is still no database, no user accounts, no server-rendered pages, no long-running process to operate.
  - **Has to change:** the HTML file needs a small amount of new code to (1) read an event code from config, (2) after a successful local capture, `fetch()` a presigned upload URL from the Worker and `PUT` the blob to the bucket (fire-and-forget relative to the guest's flow — the guest already has their local copy; upload happening in the background must never block or gate the existing screen flow, per "a crash mid-recording is a real loss" in CLAUDE.md), and (3) for instant share specifically, request a read-scoped presigned URL and render it into a QR code on the Thank You screen (a client-side QR generator, e.g. a small dependency-free canvas-based QR encoder, is a reasonable, contained exception to "no dependencies" — flag to developer as a decision point, not an assumption).
  - **This does not need "something more"** than client-heavy + thin serverless layer for the sizes involved here (one venue, one event, tens to low hundreds of captures). It would need something more (real backend with a database, auth, job queue) only if grao grows into: multiple simultaneous events needing a shared admin view, server-side processing (e.g. auto-compiling the "edited compilation" Premium feature), or account-based client login to the gallery instead of a link. None of that is in scope here — explicitly flag it as a non-goal for this phase so developer doesn't over-build the Worker into a mini-API.

### Consumer-specific notes

- **#1 Delivery backend:** upload-only presigned URLs, background upload after existing local save, per-event folder. Gallery delivery to the couple is *still* out of scope as an in-app feature per CLAUDE.md's business context ("assume delivery happens out-of-band... until told otherwise") — this just gets the files into the cloud folder; sending the couple a link is still a manual founder action for now (e.g. share the R2 folder or a simple listing page) unless/until that's separately scoped.
- **#2 Instant guest share:** read-scoped presigned URLs with a **short TTL** (hours, not indefinite) and a page that offers save/share-sheet, not a permanent public gallery page per capture — see Risks below on why indefinite/public URLs are the actual danger here, not the QR code mechanism itself.
- **#3 QR remote recording:** unchanged from its own file; now explicitly consumes the same bucket/function rather than a separate one.

### New risks this introduces (beyond "is it worth building")

- **GDPR/consent, Portugal/EU:** guest video/photo is personal data (arguably special-category-adjacent if it captures likeness at a wedding with identifiable third parties, though not sensitive-category under GDPR strictly). Today, "capture → local file → operator hands off after event" never sends anyone's face/voice off-device. The moment capture uploads to a third-party cloud bucket, grao becomes a data controller/processor making an active choice about where EU citizens' personal data is stored and for how long, and needs: a lawful basis (almost certainly consent, since this is optional guest participation — but consent needs to be actually gathered, not just implied by walking up to a booth), a retention/deletion policy (a bucket with no lifecycle rule effectively becomes indefinite third-party storage of wedding guests' faces — that needs an explicit TTL/deletion job, not an assumption), and a sub-processor disclosure if using a US-headquartered cloud provider (R2/Cloudflare has EU region options — use one, don't default to global). None of this exists today because there's nothing to disclose today (client-side-only, hands-off-locally). This is a materially new compliance surface, not a paperwork footnote, and should be resolved before any guest content leaves the kiosk device, not after a soft launch.
- **Instant-share-specific risk:** a read-scoped presigned URL behind a QR code is, practically, "anyone who scans this QR code or has this link can view/download this guest's photo." If the URL is long-lived or the share page is crawlable/guessable, that's an accidental public gallery of wedding guests' photos with no consent flow for the *viewer* side even if the *capturer* consented. Mitigate with short TTLs and non-enumerable capture IDs (already implied by presigned-URL design), but this needs the security review flagged in qr-remote-recording.md before shipping, not just a technical mitigation on paper.
- **Reliability/silent-failure risk (a CLAUDE.md first-class concern):** background upload over venue WiFi/hotspot can fail or stall without the guest or operator noticing, since by design it must not block the existing flow. This needs a visible-but-unobtrusive operator-facing indicator (not guest-facing — don't make guests worry about upload status on their one take) so the operator can tell "local copy: fine, cloud copy: didn't make it, do the USB handoff as backup for this file" — otherwise this quietly reintroduces exactly the failure mode CLAUDE.md's guardrails exist to prevent, just moved from capture-time to upload-time.
- **Cost/ops risk:** bucket storage and a Worker are cheap at one-event scale, but this is the first grao component with an ongoing cloud bill and an account to secure (API tokens, bucket access keys) — a new secrets-management responsibility that doesn't exist in a static-HTML-file world. Small but real, and someone (founder or developer) now owns rotating/protecting those credentials.

## Trigger to revisit (if deferred / for phased build)

- Build the shared upload-only primitive (#1 sizing) once: the admin/config layer (CLAUDE.md priority #4) exists (technical dependency), **and** either (a) manual file hand-off has caused a real complaint/delay at an actual event, or (b) a second booking is confirmed and the founder wants delivery-by-link ready for it.
- Add instant guest share (#2) only after: the #1 primitive has run successfully at a real event, **and** marketer's Voast research has come back with evidence this class of feature matters to bookings/reviews, **and** the GDPR consent/retention question above has a concrete answer (not just "we'll figure it out").
- Revisit QR remote recording (#3) per its own file's existing gate: a real Premium client confirmed to need it, unchanged by this document.
